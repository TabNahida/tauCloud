# M8: process plugins and Docker

M8 adds an administrator-only backend API and a separately supervised `taucloud_plugins` domain. The first-party Docker integration is an installable `taucloud_docker` worker, not a route to an arbitrary daemon API. The WebPanel remains M9.

## Trust and authority

The only supported execution policy is **trusted-code-only**. Installation and rollback require explicit approval of the manifest SHA256, the complete permission list, and `trusted_code: true`. No package executes on installation or upgrade; activation is a separate operation. A manifest change invalidates a prior approval. A rollback that restores permissions also needs approval. No OS sandbox has been established: native code runs as the service account and can exercise that account's OS authority. Private IPC credentials and directories provide protocol separation, not protection against malicious code sharing that account. Do not install untrusted packages.

Every management request, including GET, requires both the administrator role and the `admin` token scope. Browser writes retain Origin/CSRF checks. Plugin RPC uses the existing version 1 HMAC/nonce/generation protocol, with two private keys per installed worker; global service keys and engine configuration are not supplied to generic plugins. Docker operations are checked against both the package grants and the approved endpoint grants. Only a package whose entry executable matches the bundled Docker worker may request Docker capabilities. Permission revocation is checked again by the manager before each invocation.

## Package contract and lifecycle

A package is a local directory containing `manifest.json` and the declared native executable/resources. There is no archive extraction, shell execution, executable ABI loading, or dependency download. Package validation opens files through the confined native-file adapter, rejects symlinks/reparse points and ordinary hardlinks, checks portable paths and SHA256, and rechecks hashes while copying. Only declared files enter the installed package. Activation/restart verifies installed hashes again.

```json
{"schema":1,"id":"example","version":"1.0.0","ipc_version":1,
 "kind":"generic","entry":"worker","files":{"worker":"<64 lowercase hex SHA256>"},
 "capabilities":["plugin.invoke"]}
```

IDs are lowercase identifiers; versions are numeric MAJOR.MINOR.PATCH. `kind` is `generic` or `docker`. Supported capabilities are `plugin.invoke`, plus `docker.read`, `docker.logs`, and `docker.control` for the bundled Docker worker. Generic packages cannot request daemon authority.

Limits: eight retained plugin identities, four retained package directories per identity, 32 files per package, 64 MiB per file and 128 MiB per package. Reinstalling an identical retained package is allowed. Old inert packages are intentionally retained; when the four-version limit is reached, an administrator must remove unneeded inactive package directories while the service is stopped. Configuration/data are never recursively removed by uninstall. The Linux local socket path must fit the platform's Unix socket limit; use a short state path.

Worker arguments are `--state <private directory> --generation <32 hex>`. Private state includes `configuration/`, `data/`, `config.json`, `ipc-keys.json`, and `plugin.json`. Use the process RPC contract in `include/taucloud/core.hpp`: listen as `plugin`, accept `ping`, `stop`, and `invoke` from `plugins`; publish PID/birth/executable/generation/IPC-version identity in `plugin.instance.json`. The host validates native process identity before adoption or termination. Configuration/data survive upgrades, rollback, process/service restart and uninstall. The C++ test worker is an executable example, not an installed production plugin.

Each worker has a 256 MiB RSS budget, a four-connection IPC queue, and health probes. Five failures in 60 seconds enter `crash_loop`; exponential delays are capped at five seconds. An explicit enable resets the crash counter. Shutdown first requests a graceful stop, then terminates only the verified process. A manager restart adopts a matching live instance; durable disabled state prevents crash-window reactivation. IPC frames are capped at 512 KiB, invocation input at 64 KiB, and engine calls share a bounded request deadline. Staged/retained packages never execute without a published activation record.

## Management API

Use the existing TLS API and bearer token; all routes are under `/api/v1/plugins/`.

| Method / operation | Request |
| --- | --- |
| GET `list` | Plugin versions, desired/running status, manifests, retained previous version, endpoint summaries and trust mode |
| POST `plan` | `{"source":"/absolute/package"}`; returns manifest, digest, added permissions and trust requirements |
| POST `install` | `source`, `approved_digest`, `approved_permissions`, `trusted_code:true`; also performs an upgrade, leaving it disabled |
| POST `enable`, `disable`, `uninstall` | `{"id":"example"}` |
| POST `rollback-plan` | `{"id":"example"}`; returns the prior version and required approval |
| POST `rollback` | `id`, `approved_digest`, `approved_permissions`, `trusted_code:true`; leaves restored version disabled |
| POST `engine-plan` | `{"endpoint":{...}}`; normalizes and hashes the proposed endpoint and its authority |
| POST `engine-approve` | The same `endpoint` plus `approved_digest` |
| POST `engine-remove` | `{"id":"engine"}`; revokes future requests |
| POST `invoke` | `{"id":"docker","request":{"engine":"engine","operation":"inventory","resource":"containers"}}` |

Package the first-party worker using `python scripts/package_plugin.py --binary build/linux/x86_64/release/taucloud_docker --output /absolute/docker-package --id docker --version 1.0.0 --kind docker`. Add `--capability docker.logs` and/or `--capability docker.control` only when intended. Use the Windows `.exe` on Windows. Review the plan response, submit the exact approval, then enable the installed plugin. No administrative approval is inferred from a package's own declaration.

## Docker contract

Endpoints explicitly select `transport`, `platform` and permissions; no `DOCKER_HOST`, redirect following or arbitrary URI forwarding is used.

```json
{"id":"engine","transport":"unix","path":"/var/run/docker.sock",
 "platform":"linux-native","permissions":["docker.read"]}
```

Windows local pipes use `transport:"pipe"`, `path:"\\\\.\\pipe\\docker_engine"`, and `platform:"windows-native"` or `"linux-vm"`. Remote endpoints use `transport:"tls"`, a numeric `address`, `port`, verified `server_name`, and absolute PEM paths `ca`, `certificate`, `key`; mutual TLS is required. Their platform is `remote-linux` or `remote-windows`. Plain TCP and remote named pipes are rejected. Endpoint plans include paths, not private key contents. Configuration and credentials stay in private state; metadata backup does not export plugin packages, state or engine credentials.

The worker negotiates the intersection of its API 1.41–1.52 range and `/version`'s `MinAPIVersion`/`ApiVersion`, then checks `/info`'s `OSType` against the approved platform. See the [Docker Engine API reference](https://docs.docker.com/reference/api/engine/) and [version history](https://docs.docker.com/reference/api/engine/version-history/). All paths returned by Docker refer to the **engine's filesystem**. A Windows client connected to a Linux VM/WSL2 engine does not imply access to Windows host paths. No automatic path translation or host bind-mount creation is provided.

Operations:

- `info`: negotiated version, explicit platform/path capabilities and selected engine metadata.
- `inventory`, `resource: containers|images|volumes|networks`: at most 128 items; excessive responses fail explicitly rather than claiming a complete truncated inventory.
- `stats`, `id`: one container sample, `stream=false&one-shot=true`.
- `logs`, `id`, optional `tail` 1–1000: `follow=false`, at most 32 KiB; lossless hex bytes preserve Docker raw/multiplexed framing and content type.
- `lifecycle`, `resource`, `id`, `action`: containers support start/stop/restart/remove; images, volumes and networks support remove. Force, volume cascade and image pruning are disabled. Stop/restart timeout is 0–2 seconds. Refresh state after a timeout: the engine may already have accepted the action, and the host does not automatically retry mutations.

No create/exec/attach/build/pull, privileged options, host bind mounts, hijacked streams or arbitrary method/path/body proxy is exposed. These are explicit capability limits, not silent forwarding. Engine HTTP headers are bounded to 16 KiB and bodies to 256 KiB. Ambiguous framing, trailers, compressed responses, redirects, oversized bodies and disconnects fail closed. Reads and writes have a common deadline, including TLS handshake.

## Validation

Run `python scripts/run_m8.py --compiler gcc` (or `clang --sanitizers`, `msvc`). `tests/m8_integration.py` covers approval, escalation, private keys, lifecycle/data retention, crash quarantine, daemon permissions, API negotiation, bounded HTTP, unavailable/disconnected engines, typed operations, TLS peer checks and Unix/Windows-pipe transports using disposable protocol fixtures. Remote results and real-engine acceptance must be recorded separately; protocol fixtures are not evidence of a live Windows Docker daemon or WSL deployment.
