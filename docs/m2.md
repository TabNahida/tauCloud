# M2 identity, policy and file core

[简体中文](m2.zh-CN.md) · [API schema](openapi.json) · [Acceptance records](evidence/m2/README.md)

M2 adds users/groups, private and team spaces, share policy, four isolated storage-domain workers, durable file operations and native inventory. The local HTTPS API and C++ CLI perform actual file transfers. External WebDAV, FTP, SMB and NFS servers remain later milestones; `/capabilities` advertises no such protocol. M0 acceptance does not depend on port 445.

## Build and run

Use the pinned dependencies and initialization/bootstrap procedure in [M1](m1.md). Existing M1 identity databases migrate transactionally from schema 2 to 3 after an SQLite backup to `identity.pre-v3.db`. The supervisor adds keys for the new domain workers under its existing owner lock. Install **all** service executables together; mixed M1/M2 executables are unsupported. The `--m1=y` xmake option builds the cumulative backend including M2.

```sh
python3 scripts/fetch_pace.py
python3 scripts/fetch_pace.py --dependency recipes
python3 scripts/run_m2.py --compiler gcc --large-mib 257
python3 scripts/run_m2.py --compiler clang --sanitizers
```

Windows: `python scripts/run_m2.py --compiler msvc --large-mib 257`, or `scripts/windows_m2.ps1` for the isolated NTFS/reference-toolchain build. The runner includes M1 regression tests. Large tests deliberately restrict worker allocation to 256 MiB; do not combine the Linux hard allocation limit with ASan's shadow mappings. Tests use temporary roots, arbitrary loopback ports and no service registration. Disk-full injection is compiled into the unit-test native adapter only.

After administrator bootstrap/login (`--scope admin`), configure an existing absolute root and a newly created space. These commands use the same `BIN`/`STATE` variables as M1:

```sh
printf '%s' '{"id":"data","path":"/absolute/existing/root"}' | "$BIN/taucloud_ctl" --state "$STATE" call --method POST --path /api/v1/storage-roots --request-id register-root-0001
printf '%s' '{"id":"private","root":"data","path":"private","owner":"admin","quota":1073741824}' | "$BIN/taucloud_ctl" --state "$STATE" call --method POST --path /api/v1/spaces --request-id create-space-0001
"$BIN/taucloud_ctl" --state "$STATE" put --space private --path example.bin --file /absolute/input.bin --request-id upload-example-0001
"$BIN/taucloud_ctl" --state "$STATE" get --space private --path example.bin --file /absolute/new-output.bin
"$BIN/taucloud_ctl" --state "$STATE" call --method GET --path /api/v1/monitoring
```

Windows root bodies use a native drive path such as `C:\\taucloud-data`. Send user passwords in JSON over stdin to `POST /users`, not command-line arguments. Ordinary users log in with `--scope files` to write; `read` remains the CLI default. Generic `call` reads POST JSON from stdin. JSON examples, fields and errors are described in OpenAPI.

## Authorization and domain ownership

Management roles (`admin`, `member`) and file rights are separate. Administrators have no implicit access to another user's files. A space has exactly one user owner or group owner; owner/group membership supplies read/write rights, with additional user/group grants of `r` or `rw`. Empty grant rights remove that grant; rights are additive, not negative ACL entries. Disabling a user or changing their management role invalidates their sessions. Membership and grant changes invalidate file grants.

Identity alone owns policy tables. Each accepted change has an idempotency key, actor audit and monotonically increasing policy epoch. It pushes revocation to all domain workers with a 250 ms acknowledgement budget each. Acknowledgement follows the worker's serialized in-flight operation and clears handles/locks. Missing acknowledgement is explicit `pending`; signed grants last at most two seconds and workers reject expired grants before admitting a new operation. An already submitted native syscall cannot be rolled back by expiry. Acknowledged drain, not the expiry timestamp alone, proves that no old operation remains in flight. Repeating a committed policy request retries the revocation notification.

Root registration binds native object and volume identity. This first profile permits **one root per volume, at most four volumes**, assigned to `file`, `file_1`, `file_2`, `file_3`. It rejects nested ownership, state-directory overlap, volume roots, root replacement, mount/reparse/symlink traversal and hard-linked regular files. Space directories are newly created, never adopted from existing content. Share aliases retain the underlying space ACL, object IDs and quota; a share may narrow to a subdirectory and protocol exposure but cannot broaden authorization. A single writable protocol is allowed across a space's aliases, including direct core writes. Configuring an exposure does not start its future protocol server.

Linux uses `openat2` beneath pinned root descriptors with no symlink/magic-link/cross-mount fallback; inode/device/birth time forms native identity. Filesystems must provide birth time through `statx`. Windows uses handle-relative `NtCreateFile` and `NtSetInformationFile`, denies reparse points and retains directory handles without delete sharing. It requires a local drive path and native file IDs; UNC roots are unsupported. Native names under managed spaces use **portable-ascii-v1**: printable ASCII, case preserved but case aliases rejected, at most 120 bytes per component and 1024 bytes per path. Unicode names return `unsupported_name`; no normalization or lossy case conversion is attempted. DOS devices, alternate streams, trailing dot/space, traversal and `.tc-` names are rejected.

The dedicated OS account and private state directory remain the trust boundary. Processes isolate failures, not a malicious sibling with access to shared IPC secrets. External host writers are outside the locking/quota authority. Do not concurrently manipulate managed files with other tools; path checks cannot turn that trusted OS account into an adversarial sandbox.

## File and recovery contracts

| Area | Behavior |
| --- | --- |
| I/O | Native blocking I/O runs on bounded RPC workers. Each read/write is at most 128 KiB, offsets are signed-64-bit compatible, short I/O returns actual counts. HTTPS transfers use sequential bounded JSON/hex chunks, not a claim of WebDAV streaming. IPC frames and file HTTP bodies cap at 512 KiB; other bodies and headers remain 8 KiB. API bridge: 4 threads, 32 jobs, 16 MiB admission reservations. |
| Handles and locks | Up to 128 opaque handles and 256 byte-range write locks per domain, bound to actor, space, path and process generation. Application object IDs survive native rename and process restart. Restart invalidates handles and locks. Locks block overlapping writes by other handles; reads remain allowed. Delete and staged replacement require closed handles. File rename updates the path associated with open handles. Directory rename/delete are explicitly unavailable. |
| Quota | Logical file length plus full reservations for active uploads; aliases charge once. Replacing a file temporarily charges old plus new. Random growth checks quota before native write; the serialized authority journals uncertainty and reconciles actual lengths after failure/restart. Sparse holes count as logical bytes. `service_enforced` reports that external writes can bypass enforcement; this is not a kernel quota. |
| Whole-file upload | `begin → chunk → commit`, with hidden staging and explicit per-chunk flush. Sequential offsets; replayed chunks must match recorded bytes. Durable progress permits restart/resume. `cancel_job` removes an owned stage and releases its reservation. The CLI hashes the local source with bounded memory and binds that hash to the upload request, refusing a different source on resume. |
| Publication | Commit intent is persisted before atomic native rename. Recovery checks native object identity, target predecessor and recorded stage, including crashes just before/after publication. Committing rename/delete jobs recover similarly. Completed request IDs replay their result; conflicting IDs fail. |
| Random writes | An intent precedes native write; successful metadata/result/audit commit together. Optional `flush:true` requests durable file flush. Unknown outcomes are `uncertain_write`, never automatically replayed. Caller must inspect/reconcile before a new write intent. |
| Cross-space move | Rejected; cross-domain destinations may return `wrong_domain`, same-domain distinct spaces return `cross_volume_move_requires_copy`. No pretend atomic cross-volume rename or implicit copy/delete. Explicit copy, verify, then delete is a separate future job type. |
| Crash ambiguity | Stage-size/identity mismatch is uncertain. Unowned `.tc-stage-*` files stop reconciliation as `orphan_stage`. Provisioning intent is persisted before directory creation; a crash before its object identity is recorded yields `uncertain_provision`, never silent adoption. Preserve the fixture and inspect while stopped; no automatic destructive repair is exposed. |
| Flush boundary | Linux flushes file and affected directories; Windows flushes file data. Windows directory flush is not uniformly available, so process-crash recovery is tested without claiming directory durability under sudden power loss. |

Each domain owns `file*.db` (WAL, FULL synchronous, startup integrity check). Jobs carry actor, status, progress and reservation; writes, publication, removal and cancellation have attributable audit rows in that database. Identity's policy audit is available at `/audit`; file audit remains owner-database metadata. Job lists filter by actor and authorized subtree. SQLite recovery is not a substitute for backing up file data.

Bounded initial catalog: 1024 policy records, 1024 users, 10,000 policy request IDs, 4096 jobs per space, 100,000 random-write operation IDs per domain, 10,000 scanned entries per space and 4096 entries per directory. Limits fail closed; no history garbage collection or pagination is implemented. Do not use this preview as an unrestricted production filesystem. Metadata/audit retention needs an explicit archival policy before long-term deployment.

## Native monitoring

`GET /monitoring` requires a management administrator. CPU tick counters, memory, interface byte counters, filesystem capacity and observation timestamps come from native APIs or `/proc`/`sysfs`; derive rates from two samples. Linux reports filesystem UUID and disk WWID/serial when available, plus readable hwmon temperature. Windows reports volume GUIDs separately from physical-drive serials and queries native storage failure prediction when the driver allows it. Device indices and mount names are never presented as stable disk identities.

Collectors cap device/interface counts and check the RPC deadline. States distinguish `available`, `unavailable`, `permission_denied`, and aged sensor observations (`stale`); a temperature is not an overall-health verdict. Unsupported hardware, driver/permission restrictions and WSL virtual disks may yield no health data. The client deadline is four seconds. Native calls are blocking inside the supervised monitor process; a stalled kernel driver may require worker fencing rather than cooperative cancellation. No SMART guarantee, privileged helper, disk mutation or RAID administration is advertised.

See [the M2 decision](decisions/0005-m2-file-profile.md) for these deliberate first-profile limits and [recorded tests](evidence/m2/README.md) for what was exercised.
