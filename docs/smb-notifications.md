# SMB directory notifications

The Full SMB/NFS expansion implements SMB2 CHANGE_NOTIFY for the existing 2.1, 3.0, 3.0.2 and 3.1.1 dialects. This is an implementation increment, not a complete Samba notification conformance claim. Linux uses inotify and Windows uses overlapped ReadDirectoryChangesW on pinned directory handles. Host-side changes and writes by other protocols reach the same native stream. Portable DOS attributes, creation times, EAs and shared security descriptors add metadata events after the file-domain request commits. Initial metadata assigned by SMB CREATE belongs to the added object and does not generate separate synthetic modification events.

A notification requires a directory handle with FILE_LIST_DIRECTORY. The first request fixes the filter, recursive flag and buffer capacity for that open. Requests on one open complete in FIFO order; events remain buffered between requests. Invalid filter bits are ignored. An entirely invalid/zero filter stays pending until cancellation or handle teardown. Requests larger than the negotiated 64 KiB limit fail; a notification that cannot fit returns STATUS_NOTIFY_ENUM_DIR without partial records. Reopening establishes a new capacity.

When events are already buffered and no older request is outstanding on the open, the response completes synchronously with the original MessageId and normal credits. Later mutations belong to the next request. Otherwise the asynchronous response uses the original MessageId and its assigned AsyncId. The interim response grants credits once; final responses grant none. Finals are signed or encrypted according to their requests. CANCEL matches the supplied MessageId/AsyncId within its authenticated session. CLOSE, TREE_DISCONNECT, LOGOFF and session destruction after failed reauthentication complete notifications with STATUS_NOTIFY_CLEANUP. The failed SESSION_SETUP itself still returns its authentication error; notification finals use the old session keys before they are released. A directory marked for deletion returns STATUS_DELETE_PENDING. Policy revocation closes the authority handle and its native watches. Pending requests preserve connection liveness while still rechecking authority.

The current bounds are 16 outstanding notifications per session, a 64 KiB native buffer, 1024 events per drain and 256 queued portable metadata events per open. Linux reserves at most 96 pinned notification directories per file worker and 4096 metadata baselines per directory. Failure to cover a recursive subtree remains visibly overflowed until reopen; it never silently reports complete coverage. A new subtree populated before watches can be installed causes a rescan. Events under a subtree moved outside the watched directory are discarded and its watches removed. Private `.tc-` names are excluded.

Remaining conformance work includes exact Windows/Samba event batching, races across native rename batches, broader stream events (named streams themselves remain unimplemented), and the complete upstream notification suite. Linux uses observed metadata to distinguish SIZE from equal-length writes; it cannot reconstruct every intermediate size/access-time transition after several host operations coalesce. The original `smb2.notify.valid-req` diagnostic retains its exact event-count failure. The delete-on-close follow-up separates CREATE's per-open mode from explicit link disposition. Both original `rec` and `mask-change` now proceed beyond the previous premature DIRECTORY_NOT_EMPTY error. The recursive case next reports NOTIFY_ENUM_DIR because rapidly populated subtrees can precede inotify watch installation; the mask-change diagnostic then times out after 300 seconds awaiting a later completion. Neither is counted as passing. Existing last-open and DELETE_PENDING notification behavior remains covered by the independent suite and the original rmdir cases. See [delete-on-close implementation](m5.md) and [local evidence](evidence/pre-m8/smb-delete-close-local.json).


File-domain operations now drain native notifications before returning, including when no CHANGE_NOTIFY request is outstanding. This lets Linux install a service-created child directory's recursive watch before the next service operation populates it, while retaining overflow for uncontrollable host-side races. Native events are queued before that operation's portable metadata events. The combined per-open queue is bounded to 1024 events and 64 KiB of UTF-8 names; portable metadata still uses the 256-entry bound. Overflow discards the incomplete batch and the next successful request begins with fresh changes. Native-watch deletion remains sticky until handle teardown.

Cross-directory inotify moves now produce REMOVED/ADDED even inside one recursive watch; same-directory renames retain OLD_NAME/NEW_NAME, following [MS-FSA FileRenameInformation](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/87f86c9b-6c2a-4803-84b7-131a74a434fa). Directory watch paths follow either kind of move. The unmodified `smb2.notify.rec` passes locally and joins the regression selection; `valid-req` retains its event-count failure and `mask` retains a directory-access-time filtering failure. The previously timed-out `mask-change`, tree-path and session-reconnect gates remain open. [Local evidence](evidence/pre-m8/smb-notify-recursive-local.json) includes the intermediate recursive failure and final result. New-source cross-platform acceptance is pending.
