# SMB directory notifications

The Full SMB/NFS expansion implements SMB2 CHANGE_NOTIFY for the existing 2.1, 3.0, 3.0.2 and 3.1.1 dialects. This is an implementation increment, not a complete Samba notification conformance claim. Linux uses inotify and Windows uses overlapped ReadDirectoryChangesW on pinned directory handles. Host-side changes and writes by other protocols reach the same native stream. Portable DOS attributes, creation times, EAs and shared security descriptors add metadata events after the file-domain request commits. Initial metadata assigned by SMB CREATE belongs to the added object and does not generate separate synthetic modification events.

A notification requires a directory handle with FILE_LIST_DIRECTORY. The first request fixes the filter, recursive flag and buffer capacity for that open. Requests on one open complete in FIFO order; events remain buffered between requests. Invalid filter bits are ignored. An entirely invalid/zero filter stays pending until cancellation or handle teardown. Requests larger than the negotiated 64 KiB limit fail; a notification that cannot fit returns STATUS_NOTIFY_ENUM_DIR without partial records. Reopening establishes a new capacity.

When events are already buffered and no older request is outstanding on the open, the response completes synchronously with the original MessageId and normal credits. Later mutations belong to the next request. Otherwise the asynchronous response uses the original MessageId and its assigned AsyncId. The interim response grants credits once; final responses grant none. Finals are signed or encrypted according to their requests. CANCEL matches the supplied MessageId/AsyncId within its authenticated session. CLOSE, TREE_DISCONNECT, LOGOFF and session destruction after failed reauthentication complete notifications with STATUS_NOTIFY_CLEANUP. The failed SESSION_SETUP itself still returns its authentication error; notification finals use the old session keys before they are released. A directory marked for deletion returns STATUS_DELETE_PENDING. Policy revocation closes the authority handle and its native watches. Pending requests preserve connection liveness while still rechecking authority.

The current bounds are 16 outstanding notifications per connection, a 64 KiB native buffer, 1024 events per drain and 256 queued portable metadata events per open. Linux reserves at most 96 pinned notification directories per file worker and 4096 metadata baselines per directory. Failure to cover a recursive subtree remains visibly overflowed until reopen; it never silently reports complete coverage. A new subtree populated before watches can be installed causes a rescan. Events under a subtree moved outside the watched directory are discarded and its watches removed. Private `.tc-` names are excluded.

Remaining conformance work includes exact Windows/Samba event batching, races across native rename batches, broader stream events (named streams themselves remain unimplemented), and the complete upstream notification suite. Linux uses observed metadata to distinguish SIZE from equal-length writes; it cannot reconstruct every intermediate size/access-time transition after several host operations coalesce. The original `smb2.notify.valid-req` diagnostic retains its exact event-count failure. SMB 3.1.1 GMAC negotiation now lets Samba 4.19.5 use the original MessageId for immediate CANCEL, and `tcon` passes. The complete local diagnostic terminates with 16 successes and seven failures after the buffered-event correction (batching/filtering, share modes, reconnect/reauthentication cleanup and broader names). Windows remote acceptance at `5f536b3` rejects its first watch because ReOpenFile cannot reopen the pinned directory handle. The follow-up uses an asynchronous handle opened relative to its retained parent and verifies native identity; Windows/MSVC reacceptance passes at `682b007`, including 11 applicable independent notification groups and four signing groups ([run](https://github.com/TabNahida/tauCloud/actions/runs/41781608474)). ## Fixed-source follow-up acceptance

The targeted GCC/Clang ASan+UBSan/MSVC matrix now passes at `c6bb261`: 14/14/12 independent notification groups, two modern-rename groups and six reauthentication groups on each platform, plus 12 unmodified Samba lifecycle cases on each Linux compiler ([evidence](evidence/pre-m8/smb-notify-c6bb261-remote.json)). This includes the previously failed Windows ten-event buffered batch. The separate full upstream notification diagnostic remains failed; its pending-child deletion, path traversal, session reconnect and event-mask failures remain open.

Subsequent Clang runs at `bd6a2ad` and `6bf92f2` exposed an overly specific test expectation during policy revocation: an already-authorized poll can return ACCESS_DENIED after the file-domain epoch advances, while a later poll returns FILE_CLOSED. The corrected test accepts both denials, then requires the old handle to fail with FILE_CLOSED and a fresh exclusive read open to succeed. Local checks pass ([failure and correction](evidence/pre-m8/smb-notify-revocation-race.json)); targeted three-platform reacceptance passes at `1e92b0d` ([evidence](evidence/pre-m8/smb-nfs-1e92b0d-remote.json)).


The delete-on-close follow-up separates CREATE's per-open mode from explicit link disposition. Both original `rec` and `mask-change` now proceed beyond the previous premature DIRECTORY_NOT_EMPTY error. The recursive case next reports NOTIFY_ENUM_DIR because rapidly populated subtrees can precede inotify watch installation; the mask-change diagnostic then times out after 300 seconds awaiting a later completion. Neither is counted as passing. Existing last-open and DELETE_PENDING notification behavior remains covered by the independent suite and the original rmdir cases.
