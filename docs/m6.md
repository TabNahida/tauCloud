# M6 — SMB3 backend preview

M6 extends the [M5 file/credential profile](m5.md) with independently negotiated SMB 3.0, 3.0.2 and 3.1.1. The same isolated SMB worker, file authority, identity grants, quota, share modes, byte locks, delete recovery and protected credential enrollment remain in use. No schema/config migration or credential re-enrollment is required for the M5 → M6 upgrade. Deployment still uses the configured loopback `smb_port`; functional acceptance uses disposable non-445 ports.

## Negotiated security profile

| Dialect | Signing | Encryption | Negotiation integrity |
| --- | --- | --- | --- |
| 2.1 compatibility | HMAC-SHA256 | unavailable | Legacy profile; no SMB3 preauthentication |
| 3.0 | AES-128-CMAC | AES-128-CCM | Signed FSCTL_VALIDATE_NEGOTIATE_INFO |
| 3.0.2 | AES-128-CMAC | AES-128-CCM | Signed FSCTL_VALIDATE_NEGOTIATE_INFO |
| 3.1.1 modern default | AES-128-CMAC | AES-128-GCM preferred, AES-128-CCM fallback | SHA-512 preauthentication transcript |

The server selects the highest common supported dialect. An explicit older-dialect offer remains supported; “default 3.1.1” is not a minimum-dialect restriction. SMB1 and 2.0.2 are not implemented. Signing is required for authenticated unencrypted requests. Encryption is available to SMB3 clients and responses to encrypted requests are encrypted. The server does **not** force all sessions/shares to encrypt; confidentiality-sensitive clients must require encryption and an appropriate minimum dialect. Negotiating SMB3 alone does not imply encrypted file traffic.

For 3.1.1 the bounded profile requires SHA-512 and an offered AES-128 GCM/CCM cipher. If signing capabilities are supplied, AES-CMAC must be offered; when omitted the dialect's AES-CMAC default applies. Unknown bounded contexts are ignored; duplicate, overlapping/truncated or excessive contexts fail. Unsupported algorithm sets fail without silently selecting an older dialect. AES-256, GMAC, compression and transport extensions are not advertised. 3.0/3.0.2 encryption is usable only when the client advertises its encryption capability.

The preauthentication chain includes the exact SMB NEGOTIATE request/response and SESSION_SETUP exchanges through the final authentication request. The successful SESSION_SETUP response is signed with the derived key, but excluded from the key derivation transcript. SP800-108 HMAC-SHA256 derives distinct signing, client-to-server and server-to-client keys. 3.0/3.0.2 use their dialect-specific labels/contexts; 3.1.1 uses the transcript hash. NTLMv2 MIC and the M5 credential vault remain mandatory. Authentication failure ends the connection, avoiding accidental reuse of a partial transcript.

Validate-negotiate compares the complete original client dialect list, capabilities, GUID and security mode; mismatch closes the connection. Sending that IOCTL on 3.1.1 closes the connection as specified by MS-SMB2. An explicit legacy-only offer cannot be distinguished from an application choosing legacy compatibility: clients must enforce their own minimum/encryption policy.

## Message safety and lifecycle

AES-CCM/GCM authenticates the transform header (including session, nonce and original length) and payload before any command executes. Invalid tags, headers, session IDs, nested transforms/compression and malformed compounds fail closed. All compound segments are validated before executing the first operation. Credit-window MessageIds reject duplicate/old commands for signed and encrypted traffic. Received nonces are tracked per session; reuse is rejected even with a fresh MessageId. Outbound nonces combine a random prefix with a strictly increasing counter. Each direction is capped at 65,536 encrypted frames per session; clients must reconnect at that bound. This deliberately bounds replay memory and nonce lifetime; automatic rekey is not implemented.

Bounds remain those of M5, with up to 1 MiB plaintext plus a 52-byte encryption header, 16 compound operations, 64 KiB read/write payload, at most 32 connections, one authenticated session per connection and 60-second idle timeout. Keys are volatile and cleared at connection cleanup. Disconnect/crash closes ordinary handles and releases locks; committed delete intents are reaped by the file authority. Restart creates new session IDs/keys and requires authentication plus reopen. Transparent failover and persistent sessions are not promised.

| Separate capability | M6 decision |
| --- | --- |
| Durable/persistent handles | No grant; durable reconnect fails explicitly |
| Leases/oplocks/directory caching | No grant; ordinary uncached opens only |
| CHANGE_NOTIFY | Unsupported; callers can re-query |
| Multichannel/session binding | Not advertised; binding rejected |
| DFS, RDMA, compression, POSIX, persistent ACLs | Not implemented |

## Use and reproduce

Configure/enroll with the [M5 instructions](m5.md). `GET /api/v1/protocols` now reports all four supported dialects, AES-CMAC, ciphers, preauthentication and the encryption policy. For example, using the pinned test client:

```python
connection = Connection(uuid.uuid4(), "127.0.0.1", port, require_signing=True)
connection.connect()  # 3.1.1 selected when offered
session = Session(connection, username="TAUCLOUD\\alice", password=password,
                  require_encryption=True, auth_protocol="ntlm")
session.connect()
```

```sh
.deps/smbprotocol-venv/bin/python scripts/run_m6.py --compiler gcc --large-mib 17
.deps/smbprotocol-venv/bin/python scripts/run_m6.py --compiler clang --mode debug --sanitizers
```

Use `scripts/windows_m6.ps1` for a disposable native NTFS/MSVC checkout. The pinned `tests/smb-requirements.txt` installs smbprotocol/pyspnego and Windows SSPI support. The runner includes all M1–M6 checks; `--litmus` adds M3 WebDAV regression. See [evidence](evidence/m6/README.md) for actual runs. This selected backend profile does not claim Explorer/kernel SMB/macOS interoperability, Samba torture compliance, or a large-volume soak test.
