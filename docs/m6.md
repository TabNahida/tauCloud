# M6 — SMB3 backend preview

M6 extends the [M5 file/credential profile](m5.md) with independently negotiated SMB 3.0, 3.0.2 and 3.1.1. The same isolated SMB worker, file authority, identity grants, quota, share modes, byte locks, delete recovery and protected credential enrollment remain in use. No schema/config migration or credential re-enrollment is required for the M5 → M6 upgrade. Deployment still uses the configured loopback `smb_port`; functional acceptance uses disposable non-445 ports.

## Negotiated security profile

| Dialect | Signing | Encryption | Negotiation integrity |
| --- | --- | --- | --- |
| 2.1 compatibility | HMAC-SHA256 | unavailable | Legacy profile; no SMB3 preauthentication |
| 3.0 | AES-128-CMAC | AES-128-CCM | Signed FSCTL_VALIDATE_NEGOTIATE_INFO |
| 3.0.2 | AES-128-CMAC | AES-128-CCM | Signed FSCTL_VALIDATE_NEGOTIATE_INFO |
| 3.1.1 modern default | AES-128-GMAC/CMAC or HMAC-SHA256 | AES-128/256-GCM/CCM; AES-128-GCM preferred | SHA-512 preauthentication transcript |

The server selects the highest common supported dialect. An explicit older-dialect offer remains supported; “default 3.1.1” is not a minimum-dialect restriction. SMB1 and 2.0.2 are not implemented. Signing is required for authenticated unencrypted requests. Encryption is available to SMB3 clients and responses to encrypted requests are encrypted. The server does **not** force all sessions/shares to encrypt; confidentiality-sensitive clients must require encryption and an appropriate minimum dialect. Negotiating SMB3 alone does not imply encrypted file traffic.

For 3.1.1, SHA-512 preauthentication is mandatory. Encryption is negotiated independently: an absent encryption context is omitted from the reply; an offered list without a common AES-128/256 GCM/CCM cipher receives one cipher ID of zero. Both permit authenticated signed sessions, while encrypted transforms are rejected without a negotiated cipher. There is no implicit cipher or older-dialect fallback. Signing capabilities select AES-GMAC, AES-CMAC or HMAC-SHA256 in that preference order; absent or non-overlapping signing offers select mandatory AES-CMAC. Empty/malformed algorithm lists fail. GMAC nonces combine MessageId with direction and CANCEL bits for synchronous and asynchronous responses. Missing preauthentication and duplicate singleton contexts (types 1, 2, 3, 7, 8) fail; repeated NETNAME, unsupported transport and unknown contexts are ignored after bounds validation. Truncated, overlapping or excessive contexts fail. Compression and transport extensions are not advertised. 3.0/3.0.2 encryption requires the client's encryption capability. See [MS-SMB2 negotiation processing](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/b39f253e-4963-40df-8dff-2f9040ebbeb1).

The preauthentication chain includes the exact SMB NEGOTIATE request/response and SESSION_SETUP exchanges through the final authentication request. The successful SESSION_SETUP response is signed with the derived key, but excluded from the key derivation transcript. SP800-108 HMAC-SHA256 derives distinct signing, client-to-server and server-to-client keys. 3.0/3.0.2 use their dialect-specific labels/contexts; 3.1.1 uses the transcript hash. NTLMv2 MIC and the M5 credential vault remain mandatory. Authentication failure ends the connection, avoiding accidental reuse of a partial transcript.

Validate-negotiate compares the complete original client dialect list, capabilities, GUID and security mode; mismatch closes the connection. Sending that IOCTL on 3.1.1 closes the connection as specified by MS-SMB2. An explicit legacy-only offer cannot be distinguished from an application choosing legacy compatibility: clients must enforce their own minimum/encryption policy.

## Message safety and lifecycle

AES-CCM/GCM authenticates the transform header (including session, nonce and original length) and payload before any command executes. Invalid tags, headers, transform session IDs, nested transforms/compression and malformed compounds fail closed. All compound segments are validated before executing the first operation. Credit-window MessageIds reject duplicate/old commands for signed and encrypted traffic. Received nonces are tracked per session; reuse is rejected even with a fresh MessageId. Outbound nonces combine a random prefix with a strictly increasing counter. Each direction is capped at 65,536 encrypted frames per session; clients must reconnect at that bound. This deliberately bounds replay memory and nonce lifetime; automatic rekey is not implemented.

Bounds remain those of M5, with up to 1 MiB plaintext plus a 52-byte encryption header, 16 compound operations, 64 KiB read/write payload, at most 32 connections, up to 16 sessions per connection and a 60-second idle timeout. Keys are volatile and cleared at connection cleanup. Disconnect/crash closes ordinary handles and releases locks; committed delete intents are reaped by the file authority. Restart creates new session IDs/keys and requires authentication plus reopen. Transparent failover and persistent sessions are not promised.

| Separate capability | M6 decision |
| --- | --- |
| Durable/persistent handles | No grant; durable reconnect fails explicitly |
| Leases/oplocks/directory caching | No grant; ordinary uncached opens only |
| CHANGE_NOTIFY | Native asynchronous events with signed/encrypted completion; [bounds and remaining conformance](smb-notifications.md) |
| Multichannel/session binding | Not advertised; binding rejected |
| Persistent ACLs | Simple owner/group/DACL support; [remaining conformance](file-security.md) |
| DFS, RDMA, compression, POSIX | Not implemented |

## Use and reproduce

Configure/enroll with the [M5 instructions](m5.md). `GET /api/v1/protocols` now reports all four supported dialects, AES-CMAC, ciphers, preauthentication and the encryption policy. For example, using the pinned test client:

```python
connection = Connection(uuid.uuid4(), "127.0.0.1", port, require_signing=True)
connection.connect()  # 3.1.1 selected when offered
session = Session(connection, username="TAUCLOUD\\alice", password=password,
                  require_encryption=True, auth_protocol="ntlm")
session.connect()
```

```sh
.deps/smbprotocol-venv/bin/python scripts/run_m6.py --compiler gcc --large-mib 17
.deps/smbprotocol-venv/bin/python scripts/run_m6.py --compiler clang --mode debug --sanitizers
```

Use `scripts/windows_m6.ps1` for a disposable native NTFS/MSVC checkout. The pinned `tests/smb-requirements.txt` installs smbprotocol/pyspnego and Windows SSPI support. The runner includes all M1–M6 checks; `--litmus` adds M3 WebDAV regression. See [evidence](evidence/m6/README.md) for actual runs. This selected backend profile does not claim Explorer/kernel SMB/macOS interoperability, Samba torture compliance, or a large-volume soak test.

## AES-256 expansion

SMB 3.1.1 also negotiates AES-256-CCM (3) and AES-256-GCM (4), including clients offering only one of these ciphers. Server preference remains AES-128-GCM, AES-128-CCM, AES-256-GCM, AES-256-CCM. SMB 3.0/3.0.2 retain AES-128-CCM. CCM uses an 11-byte nonce; GCM uses 12 bytes. Both directions retain distinct keys and the existing nonce replay/counter limits.

Signing still derives from the 16-byte SMB SessionKey. AES-256 encryption/decryption derives 32 bytes using the complete authentication key (FullSessionKey), the appropriate directional label and SHA-512 preauthentication transcript. A 32-byte Kerberos key must not be truncated first. NTLM's 16-byte exported key is accepted by the KDF; selecting an AES-256 cipher does not increase the entropy of that authentication key. Session renewal retains the original signing/encryption keys and nonce history.

Independent frozen KBKDFHMAC/AESCCM/AESGCM vectors cover both key sizes, key-length rejection and every-byte transform tampering. The smbprotocol tests force each AES-256 cipher, verify encrypted I/O and renewal, decode raw transforms independently and reject modified tags/nonces/lengths/session IDs/ciphertext and replay. Real MIT Kerberos/SPNEGO tests separately verify full 32-byte input keys. GCC/Clang ASan+UBSan/MSVC targeted acceptance passes at `682b007` ([evidence](evidence/pre-m8/smb-security-682b007-remote.json)). The subsequent cipher-free negotiation extension passes 1,137 core checks and 23 independent client groups locally; its targeted GCC/Clang ASan+UBSan/MSVC acceptance passes at `1e92b0d` ([evidence](evidence/pre-m8/smb-nfs-1e92b0d-remote.json)).

[Local AES-256 evidence](evidence/pre-m8/smb-aes256-local.json): 793 core checks, 20 SMB3 groups and 12 real Kerberos/SPNEGO groups pass.

SMB sessions now have independent authentication exchanges, preauthentication transcripts, signing/cipher keys, replay nonces, trees, opens and asynchronous requests on one transport. Credits and AsyncIds remain connection-wide. Failed new authentication leaves other sessions usable. A verified `PreviousSessionId` replaces only the same canonical user's old session, completes its pending notifications with the old keys, closes its opens and logs out its token; unrelated sessions and the old transport survive. Reciprocal replacements hand off cooperative gates to avoid a cycle. Abandoned unauthenticated contexts expire after ten seconds, and transport teardown drains all contexts. Independent tests cover all four dialects, scoped file IDs/CANCEL, queued locks, rename propagation, wrong-key rejection, replacement races and capacity reuse. This does not implement multichannel binding or durable handles ([local evidence](evidence/pre-m8/smb-multisession-local.json)).

Session handling follows [MS-SMB2 per-session state](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/fbcbc952-8c1f-4528-a0ab-7aed7d52264e) and [authentication and previous-session removal](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/5ed93f06-a1d2-4837-8954-fa8b833c2654).
